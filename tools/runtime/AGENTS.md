# Agent：把资源观测用于实际任务

代码记录并核对资源，命令和字段见README；Agent落实以下执行目标，不另建通用调度器。

- 先核授权、宿主/容器和设备UUID。capture须在可观察GPU宿主PID及其/proc祖先的环境运行；先确认空闲采样。先核实未使用MPS或合并调用者的代理；仅凭整卡或进程类型不够，未知时不采纳证据。前台任务根须专属本任务并覆盖全部GPU子进程，实际核其PID/启动tick；不能用容器init、共享shell或代理server扩大白名单。
- 按用户授权、环境/作业限制和任务成本设置并记录有限期限，在实际执行环境落实期限和本人任务收尾；可使用已验证的原生timeout或现有作业机制。Docker客户端被停不等于容器工作结束；首次环境要做短故障演练。只清理自己创建且身份核实的进程，未知时停止重试。
- 使用当前gpu_watch时，单次capture的`--seconds`上限为3600秒，check要求完整覆盖任务及前后采样；任务期限须预留相应余量。更长任务须先有受支持且验证过的连续覆盖/监督方案，不能只放大参数或把部分采样当完整覆盖。工具上限不是用户授权或整轮预算。
- 保存实际命令、环境、任务根身份、起止时刻、退出码、日志及收尾证据；原生工具不能直接提供时只补本次最小接线。容器PID必须核到宿主，时钟/boot_id也须匹配。
- 首次登记本人进程也须核身份：旧的进程列表只能发现PID，不能把该PID当前的启动tick直接登记成本人。根进程应在稳定身份前后核专属命令、执行用户与容器/作业归属，子进程核当前稳定的祖先链；已登记身份不可被新tick覆盖。支持pidfd时可绑定同一内核进程再发信号，仍须先证明归属。正常退出、客户端提前退出及中断均核已登记本人进程收尾。
- 运行中检查新采样；发现竞争/监测失效时本次计时作废，按期限或显式停止本任务；停止方式取决于真实环境，不自动杀外来PID。长时间工具等待不能替代监测。
- 原始计时须绑定实际生成它的worker/运行、输入/配置、输出名单与内容身份及相应监督/退出/收尾。恢复或append逐来源核验；后一个成功作业不能给前一个受扰或失败作业的样本背书。原记录缺归属证据时明确未验证，不能只凭文件放在同一目录或时间接近认可。
- 任务结束且取得后侧采样后，停止capture并确认退出，再运行check。仅命令成功、resources_clear通过且本人任务已收尾三者齐全，才接受性能数据；原始失效产物保留。资源通过不代表预热、稳定性或质量通过。
- 等待设备、重试与恢复由Agent按预算推进，使用新目录；恢复先核进程/期限/已有产物。不把Agent适配说成工具自动支持，不为未知环境不断增加公共分支；成熟通用机制再提炼。
- 工具或指南改动的回归按变化范围和风险选择验证，核外来进程、缺采样、PID复用、期限及仅本人收尾；不为未变能力重复GPU矩阵。模型优化任务的实验覆盖与执行范围按用户目标和探索计划确定。

采样传输若在模型释放或驱动退出阶段阻塞，保留整组失效记录，不能裁掉退出区间。替换传输须对照实际宿主PID可见性、显存字段与进程类型，保持原准入和覆盖要求；例如不同NVML版本的used字段可能是否包含driver reserved不同，不能用放宽空闲阈值掩盖语义变化。替代实现属于任务接线，验证成熟前不宣称gpu_watch已原生支持。

绕过解释器正常退出的接线须核库的真实收尾机制：同步CUDA/NCCL并不清理依赖atexit的编译工作池。若确需显式结束，先在当前安装版本核相应shutdown API并验证CPU子进程收尾；释放GPU上下文后仍保持监测到任务进程退出。不要把仍可能执行CUDA/NCCL的阶段称为纯CPU退出。
