# 新平台适配与结果交付

本文供接手工程师和Agent使用。普通运行步骤只在README维护。

## 当前边界

- 当前实际实现并验证的平台是MLU；A100/CUDA尚未实现，不能通过复制MLU JSON或删除平台检查来宣称支持。
- `common/suite.json`固定40对象、输入顺序、seed、5视图/512流程、BF16策略和两次重复；原始模型、LightX2V、不同平台共用相同输入和权重。
- 时间覆盖读图、预处理、模型、必要CPU处理及CPU输出；加载、预热、保存、指标和导出分别计时或排除。跨平台沿用相同边界。
- LightX2V源码和参考源码按提交及文件哈希固定。MLU参考实现带有明确兼容修改，不能冒称未经修改的CUDA原项目。

## 1. 在动代码之前固定实验身份

1. 阅读本项目README、DATA和configs说明，并检查目标模型已有`scripts/`和`configs/platforms/`的实际接口。
2. 对A100等NVIDIA平台，先读仓库`tools/runtime/AGENTS.md`与README；整卡/PID归属观测优先复用`gpu_watch.py`。核心算子诊断按`tools/benchmarks/AGENTS.md`，算子成绩不能替代本项目整模精度和延迟。
3. 记录卡型/显存、设备UUID、驱动、CUDA或厂商运行时、Python、PyTorch、Attention及稀疏库版本、镜像ID/digest、源码提交和权重SHA256。记录MIG/MPS或容器设备映射状态，不能只写“A100”。
4. 复用已经冻结的GSO同步视图包。将源数据包、权重及SHA清单传到新机器；A100无法访问原文件系统时使用独立包及哈希校验，不保留另一台机器的绝对路径作为默认配置。
5. 如果模型版本、量化、输入尺寸、视图、采样步数或精度策略发生变化，作为新的实验版本记录；不继续使用旧标签混合统计。

## 2. 新平台必须补的代码与配置

建议目录为`configs/nvidia/a100/`，其他卡型使用各自同级目录。公共输入与公式继续在`configs/common/`。

| 项目 | 需要完成的工作 |
|---|---|
| 配置选择 | 为CLI增加显式平台选择，使`CONFIG_LOCATIONS`、配置读取及快照复制选择目标目录；保留MLU默认和兼容性测试。不要把文件命名为A100却继续固定读mlu。 |
| runtime.json | 选择真实可用的CUDA/PyTorch镜像和Python路径，固定依赖；配置NVIDIA容器设备映射、CUDA_VISIBLE_DEVICES与监控。不能保留`/dev/cambricon_*`或MLU镜像。 |
| model.json | 采用模型仓库的NVIDIA预设，核对Attention等backend的真实可用性。不要默认所有精度或后端都已经在目标卡验证。 |
| 设备操作 | `seed_all`、参考模型`.to()`/autocast、同步、Event、峰值allocated/reserved、缓存清理等必须按平台分派；CUDA使用实际`torch.cuda`接口。CPU指标进程不得映射加速卡。 |
| 参考实现 | 使用固定的官方CUDA版本或明确标注的CUDA适配。不要对CUDA原项目套用MLU兼容补丁；生成本平台source-lock和准备清单。 |
| Sparse/几何 | 对TRELLIS.2核对稀疏卷积、邻居映射、deform/grid-sample、网格解码等实际调用链；若存在CPU回退，保留日志并计入原有时间边界。 |
| paths/锁 | paths使用本机数据根或相对目录；source-lock记录目标实现版本、补丁和逐文件哈希；evaluation-origin只列本平台真实历史来源。 |
| 来源验证 | 新平台配置哈希、模型配置哈希、实际镜像、版本和设备身份写入环境及manifest。旧MLU时间不可复制成CUDA时间；旧别名只能表示已经证明不改输入/计算的元数据迁移。 |

当前`load_platform_config()`只接受MLU。新增后端时同时修改这个检查、上表代码和测试，不仅放宽检查。

## 3. 测试顺序与完成标准

1. CPU测试覆盖指标语义、API桥接、临时钩子恢复、异常/缺失报告、配置分派、设备隔离、源码准备及递归快照；保留原MLU回归。
2. 从仅包含Git提交文件的目录开始，运行源码准备、依赖安装和输入检查，确认没有依赖`history/`、预装runtime、旧sources或某台机器的路径。
3. 在目标真实硬件运行`--smoke`对应完整流程：每实现1次预热、同一对象2次正式运行；检查张量shape/finite、请求数、真实前向/采样次数、重复差值、跨实现差值、质量、时间/显存及导出。
4. 对受改动影响的算子/组件先声明比较参考、误差度量和容差，再做对应数值验证。固定seed不等于确定性，报告实际差值；不要为了得到零差值替换被测中间输入。
5. smoke通过后运行完整冻结40对象，两实现在同一目标卡上先后各80次正式请求。预热不进入正式统计；失败和缺失保留在分母中。
6. 按资源工具要求为本人任务落实已验证的超时与收尾（NVIDIA单任务期限≤1小时，必要时拆分有明确清单的run）；不能只停止Docker客户端而留下模型。记录资源前/中/后采样、本人任务根与退出/收尾证据。发现竞争或监测失效时不能保留无条件有效的时间结论；原产物保留，换新run重做受影响部分。不要终止别人的任务。
7. 用实际请求集合、预测哈希、完整指标和阶段退出码确认结束；不能只看容器退出、文件名或一个成功样本。

只有真实目标硬件的完整链路通过后，才把平台标为可运行。smoke与40对象正式结果分别标注；未测的组合明确列出缺口、所缺资源及下一步。

## 4. 新平台结果如何放入后续PR

建议提交`results/<platform>/<gpu>/<run-id>/RESULTS.md`及经过检查的summary/comparison JSON，保持结果与配置/源码提交关联。先检查单文件大小，必要时只提交逐对象和聚合指标，将原始产物放到独立存储。

每份结果至少说明：对象数/输入清单哈希、seed/重复/预热、尺寸/视图/步数、dtype及后端、参考实现身份、源码/权重/配置哈希、设备/镜像/软件版本、成功/失败/缺失、精度、重复及跨实现差值、平均/中位/P95时间、时间边界、峰值显存、CPU参与和资源检查结论。

- 原始NPZ、GLB、日志、遥测、大权重、镜像、缓存及安装目录保存到独立产物存储，结果文档给出可访问位置和SHA清单。
- 提交结果摘要前清理私人主机路径、凭据和无关进程信息；不把本地日志直接整目录加入Git。
- 公共输入协议不因增加平台而覆盖；平台配置和正式结果独立新增。原结果保留原状态和来源，不静默重写。
- README保持运行说明，只更新已验证的平台入口或简短结果链接；详细 bring-up 与交付要求维护在本文和AGENTS。
- 提交前检查实际PR文件清单：`history/`、`artifacts/`、`cache/`、`runtime/`、`sources/`、`data/`及本地工作记录全部排除，包括已跟踪文件。
